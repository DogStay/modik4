# DayZ Modding Reference

Единая база знаний по моддингу DayZ Standalone: синтаксис Enforce Script, инструментарий PBO/Mikero Tools, `.layout`-файлы и конвертация PNG → PAA.

**Легенда пометок источника, используемая во всём документе:**
- **[Подтверждено: офиц. документация BI]** — взято из официальной документации Bohemia Interactive (Enfusion/Enforce Script docs, DayZ Modding docs на bistudio.com / community.bistudio.com wiki, зеркалирующей официальные данные).
- **[Подтверждено: DayZ Script API]** — взято из официального DayZ Community Script API (community wiki, зеркало официальных данных Bohemia).
- **[На основе vanilla-скриптов]** — синтаксис/паттерн наблюдается в реальных распакованных скриптах DayZ (`scripts.pbo` и др.), но не найден отдельно задокументированным.
- **[Не подтверждено / требует проверки]** — утверждение не найдено ни в одном из вышеуказанных источников на момент написания; использовать с осторожностью, проверять перед применением.

## 1. Enforce Script (синтаксис)

### 1.1 Базовый синтаксис классов и наследование

Enforce Script — объектно-ориентированный скриптовый язык движка Enfusion, синтаксически близкий к C++/Java. **[Подтверждено: офиц. документация BI]**

```csharp
// Basic class declaration and inheritance
class MyBaseClass
{
    protected int m_Value;

    void MyBaseClass(int value)
    {
        m_Value = value;
    }

    int GetValue()
    {
        return m_Value;
    }
}

class MyDerivedClass: MyBaseClass
{
    void MyDerivedClass(int value): super(value)
    {
    }
}
```

Ключевые модификаторы и конструкции: **[Подтверждено: офиц. документация BI]**

- **`modded class`** — расширение существующего класса без переопределения оригинального файла (модификация "поверх" ванильного или другого мода). Используется для изменения поведения ванильных классов без прямого редактирования исходников игры.

  ```csharp
  // Extends the vanilla ItemBase without touching original scripts
  modded class ItemBase
  {
      override void OnStoreSave(ParamsWriteContext ctx)
      {
          super.OnStoreSave(ctx);
      }
  }
  ```

- **`override`** — переопределение метода родительского класса. Обязателен при переопределении виртуального метода в Enforce Script (в отличие от C++, где `virtual`/`override` необязательны).
- **`super`** — вызов реализации родительского класса (метода или конструктора).
- **`sealed`** — запрещает дальнейшее наследование класса или переопределение метода.
- **`native`** — класс/метод реализован на стороне движка (C++), скриптовая часть — лишь объявление сигнатуры.
- **`proto`** — объявление функции, реализованной нативно (движком), без тела в скрипте; часто идёт вместе с `native`.
- **`autoptr`** — автоматический указатель на объект-ссылку (`ref`) с автоматическим управлением временем жизни в пределах области видимости.
- **`ref`** — указатель с подсчётом ссылок (reference-counted pointer); объект уничтожается автоматически, когда последняя ссылка на него исчезает.
- **`array<T>`** — обобщённый (generic) динамический массив, например `array<string>`, `array<ItemBase>`.
- **`typename`** — тип, представляющий имя класса как значение (используется, например, для рефлексии/фабрик через `ClassName.Cast()` или динамическое создание объектов).

```csharp
// ref / autoptr / array / typename usage
autoptr array<ref MyBaseClass> m_Items = new array<ref MyBaseClass>;

void AddItem(typename type)
{
    Print(type.ToString());
}
```

### 1.1.1 Бинарное выражение нельзя разрывать переносом строки

**[Подтверждено экспериментально: сборка JobsMod, 09.08.2026]**

Длинное выражение **должно целиком помещаться на одной строке.** Разрыв в
середине бинарного выражения не компилируется — независимо от того, с какой
стороны от переноса стоит оператор.

Правило касается **любого** бинарного оператора, а не только склейки строк
через `+`: `&&`, `||`, сравнения. Текст ошибки при этом каждый раз разный, что
и мешает узнать одну и ту же причину — см. таблицу ниже.

```csharp
// Ошибка: Invalid statement ')' на строке с ", прогресс="
Print("статус=" + view.m_Status.ToString()
    + ", прогресс=" + view.m_Progress.ToString() + ".");

// Тоже ошибка: Syntax error на строке, оканчивающейся на '+'
Print("статус=" + view.m_Status.ToString() +
    ", прогресс=" + view.m_Progress.ToString() + ".");

// Работает: одна строка, какой бы длинной она ни была
Print("статус=" + view.m_Status.ToString() + ", прогресс=" + view.m_Progress.ToString() + ".");
```

Парсер завершает инструкцию на переносе строки, и дальше сообщение зависит
только от того, где оказался оператор:

| Оператор | Где | Что видит парсер | Сообщение |
|---|---|---|---|
| `+` | в начале следующей строки | `+ "..." + "..."` — унарный плюс, валиден сам по себе, затем `)` в позиции начала инструкции | `Invalid statement ')'` на **следующей** строке |
| `+` | в конце предыдущей строки | бинарный `+` без правого операнда | `Syntax error` на **этой** строке |
| `&&`, `\|\|` | в начале следующей строки | `&&` в позиции, где ожидается начало объявления | `Unknown type '&&'` на **этой** строке |

Сообщения указывают на строку с оператором, а не на настоящую причину — сам
факт переноса. Формулировки настолько разные, что три вхождения одной и той же
ошибки легко принять за три несвязанные проблемы; надёжнее искать не по тексту
сообщения, а по строкам, начинающимся или заканчивающимся оператором:

```bash
grep -rnE '^[[:space:]]*(&&|\|\||\+|==|!=|>=|<=)' Scripts/
grep -rnE '(&&|\|\||\+|==|!=|>=|<=)[[:space:]]*$' Scripts/
```

Перенос **внутри незакрытых скобок** работает нормально: там парсер знает, что
инструкция не закончена.

```csharp
// Так можно: разрыв после '(' и после запятых
list.Insert(new MyClass(
    a, b, c,
    d, e, f));
```

Как это было установлено. Сначала предполагалось, что дело в позиции оператора,
и все 62 переноса в моде были переписаны с оператором в конце строки — ошибка
осталась, только сменила текст с `Invalid statement ')'` на `Syntax error` и
сдвинулась на строку вверх, ровно вслед за правкой. Это и опровергло гипотезу о
позиции оператора: не компилируются оба варианта. Остальные подозреваемые
конструкции из той же инструкции (`объект.поле.ToString()`, строковый литерал
`"/"`, кириллица) встречались выше по файлу и компилировались, а `3_Game`, где
переносов в выражениях не было вовсе, собирался целиком. После склейки всех 62
выражений в одну строку модуль собрался.

### 1.1.2 `owned` — ключевое слово, а не свободное имя

**[Подтверждено экспериментально: сборка JobsMod, 09.08.2026]**

`owned` — модификатор параметра в Enforce (передача владения, встречается в
объявлениях `proto native`). Как имя переменной он не парсится:

```csharp
// Ошибка: Broken expression (missing ';'?)
EntityAI owned = FindOwnedParcel(player);

// Работает
EntityAI ownedParcel = FindOwnedParcel(player);
```

Зарезервирован ровно токен `owned`; `ownedParcel`, `ownedBy` и прочие имена с
этим корнем — обычные идентификаторы.

Сообщение указывает на строку объявления, и строка выглядит совершенно
безобидно — в этом и подвох. Если `Broken expression` показывает на строку, где
явно нет ни одной ошибки, стоит проверить имя объявляемой переменной по списку
ключевых слов: `owned`, `out`, `inout`, `ref`, `autoptr`, `notnull`, `proto`,
`native`, `typename`, `event`, `thread`.

### 1.2 Жизненный цикл `EntityAI` / `ItemBase`

**[На основе vanilla-скриптов]** (структура наблюдается в vanilla `EntityAI.c`, `ItemBase.c`; отдельная сводная таблица жизненного цикла как единый документ BI не обнаружена в рамках доступных источников — **[требует проверки]** по каждому конкретному хуку у актуальной версии DayZ Script API).

Основные точки жизненного цикла:

- **Конструктор (`void ClassName()`)** — вызывается при создании объекта скрипта; используется для инициализации полей, не зависящих от состояния игрового мира.
- **`Init()`** — общая инициализация; у разных классов сигнатура и момент вызова отличаются, для многих Item/Entity классов вызывается после размещения объекта в мире.
- **`EEInit()`** — событие движка (Entity Event), вызывается при инициализации сущности в мире (и на клиенте, и на сервере, в зависимости от контекста). **[На основе vanilla-скриптов]**
- **`EEDelete(EntityAI parent)`** — событие движка при удалении сущности; место для очистки ресурсов, отмены таймеров, RPC-подписок и т.д. **[На основе vanilla-скриптов]**
- **`OnStoreSave(ParamsWriteContext ctx)`** / **`OnStoreLoad(ParamsReadContext ctx, int version)`** — сериализация состояния предмета при сохранении/загрузке игрового мира (persistence). При переопределении в `modded class` обязательно вызывать `super.OnStoreSave(ctx)` / `super.OnStoreLoad(ctx, version)`, иначе цепочка сохранения родительских классов будет нарушена. **[На основе vanilla-скриптов]**

```csharp
// Typical persistence override pattern seen in vanilla ItemBase-derived classes
modded class MyCustomItem
{
    override void OnStoreSave(ParamsWriteContext ctx)
    {
        super.OnStoreSave(ctx);
        ctx.Write(m_Value);
    }

    override bool OnStoreLoad(ParamsReadContext ctx, int version)
    {
        if (!super.OnStoreLoad(ctx, version))
            return false;

        if (!ctx.Read(m_Value))
            return false;

        return true;
    }
}
```

- **RPC (`SendRPC` / `OnRPC`)** — межсетевое взаимодействие клиент/сервер. `EntityAI` предоставляет `GetGame().RPCSingleParam(...)` / аналогичные вызовы для отправки, и метод `OnRPC(PlayerIdentity sender, int rpc_type, ParamsReadContext ctx)` для приёма. Конкретные сигнатуры варьируются между версиями API — **[требует проверки]** по актуальной версии DayZ Script API перед использованием в продакшн-коде.

### 1.3 Структура `config.cpp`

**[Подтверждено: офиц. документация BI]**

```cpp
class CfgPatches
{
    class MyMod
    {
        units[] = {};
        weapons[] = {};
        requiredVersion = 0.1;
        requiredAddons[] = {"DZ_Data"};
    };
};

class CfgMods
{
    class MyMod
    {
        dir = "MyMod";
        picture = "";
        action = "";
        hideName = 0;
        hidePicture = 0;
        name = "MyMod";
        credits = "";
        author = "";
        authorID = "0";
        version = "1.0";
        extra = 0;
        type = "mod";
        dependencies[] = {"Game", "World", "Mission"};
        class defs
        {
            class engineScriptModule
            {
                value = "";
                files[] = {"MyMod/scripts/3_Game"};
            };
            class gameLibScriptModule
            {
                value = "";
                files[] = {"MyMod/scripts/4_World"};
            };
            class worldScriptModule
            {
                value = "";
                files[] = {"MyMod/scripts/5_Mission"};
            };
        };
    };
};

class CfgVehicles
{
    class Inventory_Base;
    class MyCustomItem: Inventory_Base
    {
        scope = 2;
        displayName = "My Custom Item";
        descriptionShort = "A custom item";
        model = "MyMod\data\my_item.p3d";
        weight = 100;
    };
};
```

Обязательные и ключевые поля: **[Подтверждено: офиц. документация BI]**

- **`CfgPatches`** — обязателен для регистрации аддона движком; содержит зависимости (`requiredAddons`) и версию.
- **`CfgMods`** — описывает мод для лаунчера/списка модов, привязывает пути скриптовых модулей (`defs`) к директориям исходников по слоям (`3_Game`, `4_World`, `5_Mission` — соответствуют структуре директорий скриптов DayZ).
- **`CfgVehicles`** — иерархия классов предметов/техники/существ (несмотря на название, здесь описываются и предметы инвентаря). Наследование задаётся через `class X: Y`, где `Y` — родительский класс (может быть объявлен через forward declaration `class Y;` перед использованием, если полное определение находится в другом конфиге).
- Обязательные поля класса предмета обычно включают `scope` (видимость в редакторах/арсенале: 0 — недоступен, 1 — только наследование, 2 — доступен), `model`, `displayName`. Полный список required-полей зависит от базового класса — **[требует проверки]** по конкретному родителю.

### 1.4 Скоуп выполнения: мод (`mod`) vs сервер (`server`)

**[Подтверждено: DayZ Script API]**

Скрипты Enforce Script выполняются в общем контексте, но логика может ветвиться в зависимости от того, где выполняется код — на сервере или на клиенте. Для этого используются методы `GetGame()`:

```csharp
if (GetGame().IsServer())
{
    // Server-authoritative logic: inventory changes, damage, persistence
}

if (GetGame().IsClient())
{
    // Client-side only: UI updates, local prediction, sound/visual effects
}

if (GetGame().IsMultiplayer())
{
    // Runs on dedicated/listen server in a networked session
}
```

- **`GetGame().IsServer()`** — true на dedicated-сервере и на хосте listen-сервера (host выполняет и серверную, и клиентскую логику одновременно).
- **`GetGame().IsClient()`** — true на любом клиенте, включая host в связке listen-сервера.
- Важное следствие: код, критичный для игровой логики (изменение состояния предметов, здоровья, инвентаря), должен выполняться на сервере (`IsServer()`), иначе на dedicated-сервере с несколькими клиентами возникнет рассинхронизация — клиент не имеет полномочий изменять авторитетное состояние напрямую. **[На основе vanilla-скриптов]**
- Терминологическое замечание: в вопросе используется формулировка "модный (`mod`) и серверный (`server`) скоуп" — в официальной терминологии Enforce Script нет отдельного ключевого слова `mod`-scope как языковой конструкции; разделение клиент/сервер реализуется через проверки `IsServer()`/`IsClient()` в рантайме, а не через модификаторы доступа компилятора. **[Не подтверждено / требует проверки]** — если имелось в виду что-то другое (например, разделение файлов по `CfgMods > defs` на слои 3_Game/4_World/5_Mission, см. §1.3), уточните это отдельно.

## 2. Инструментарий PBO / Mikero Tools

### 2.1 Назначение инструментов

**[На основе vanilla-скриптов / общеизвестная практика сообщества]** — Mikero Tools не являются официальным инструментарием Bohemia Interactive; это набор community-утилит (автор Mikero) для работы с форматами Bohemia (PBO, P3D, PAA и т.д.). Официальный статус: сторонний инструмент, широко используемый сообществом, но не выпускаемый BI. **[требует проверки]** актуальных названий утилит в текущей версии набора DePbo Tools/Mikero Tools, так как состав и имена CLI-инструментов менялись между версиями.

- **`extractpbo`** — распаковка (`unpack`) PBO-архива в файловую структуру для чтения/редактирования исходников.
- **`MakePbo`** / **`pboProject`** — упаковка (`repack`) директории с исходниками обратно в PBO-архив. `pboProject` — более комплексный инструмент, поддерживающий проектные файлы (`.pboproject`) с настройками исключений, подписи и т.д.
- **`rapify`** — компиляция текстового `config.cpp` в бинарный rapified-формат `config.bin`, который движок ожидает внутри PBO.
- **`derapify`** — обратная операция: декомпиляция бинарного `config.bin` обратно в читаемый текстовый `config.cpp` (используется для изучения/реверса ванильных или чужих конфигов).
- **`DePbo`** — библиотека/утилита, лежащая в основе распаковки многих других инструментов Mikero (низкоуровневый доступ к формату PBO); в некоторых сборках фигурирует как объединяющее название набора.

### 2.2 Порядок работы

**[На основе общепринятой практики сообщества]**

1. Распаковать нужный PBO (`extractpbo`) — например, `Bliss.pbo` или `dz\scripts.pbo` из установленной игры/DayZ Tools, чтобы получить эталонные vanilla-исходники для справки.
2. Разработать/отредактировать исходники мода в отдельной директории проекта (не в распакованных vanilla-файлах — те служат только справочным материалом, редактируются копии в структуре собственного мода).
3. При необходимости декомпилировать существующий `config.bin` (`derapify`) для изучения структуры, либо писать `config.cpp` с нуля по образцу.
4. Упаковать директорию мода в PBO (`MakePbo` или `pboProject`) — на этом шаге также происходит rapification `config.cpp` → `config.bin` внутри итогового архива.
5. При публикации через Steam Workshop — подписать PBO ключом (`DSSignFile`/аналогичный инструмент подписи BI, либо интегрированная функция подписи в DayZ Tools) для проверки целостности мода сервером. **[требует проверки]** конкретного инструмента подписи — это может быть отдельная утилита `DSCreateKey`/`DSSignFile` из инструментов BI, а не из набора Mikero.

### 2.3 Отличие от штатного DayZ Tools / Workbench (Addon Builder)

**[Подтверждено: офиц. документация BI]** (общий факт существования Workbench/Addon Builder как части официального DayZ Tools, доступного через Steam) / **[требует проверки]** по деталям конкретного UI-флоу.

- **DayZ Tools (Workbench, Addon Builder)** — официальный инструментарий Bohemia Interactive, распространяемый через Steam. Addon Builder внутри Workbench выполняет аналогичную упаковку PBO "из коробки", с интеграцией в общий пайплайн разработки (World Editor, Resource Manager, Object Builder для моделей и т.д.).
- **Mikero Tools** используются сообществом там, где официальный Workbench неудобен для быстрых операций командной строки, пакетной обработки множества PBO, или для реверс-инжиниринга/изучения существующих архивов (`derapify`, `extractpbo` на чужих/vanilla PBO) — сценарии, которые официальный Addon Builder не покрывает напрямую (он ориентирован на "мои исходники → мой PBO", а не на анализ чужих архивов).
- Практический вывод: для полноценной разработки с моделями/анимациями/миром (World Editor) — используется официальный Workbench; для быстрой упаковки чисто скриптовых/конфижных модов и анализа существующих PBO — часто применяется связка Mikero Tools. Это утверждение отражает распространённую практику сообщества и не задокументировано BI как рекомендация. **[Не подтверждено / требует проверки]**

## 3. Создание `.layout` файлов

### 3.1 Структура layout и иерархия widget-классов

**[Подтверждено: DayZ Script API]** (базовые классы виджетов и механизм загрузки) / **[На основе vanilla-скриптов]** (конкретные примеры разметки).

`.layout` — XML-подобный (в текстовом виде) или бинарный (rapified) файл, описывающий иерархию UI-виджетов движка Enfusion. Базовые классы виджетов, доступные из Enforce Script через `GetGame().GetWorkspace()`/`layout.LoadWidgetLayout` и класс `Widget`:

- **`GUIClass`** (иногда описывается как корневой узел разметки в текстовом layout) — не подтверждён как формальный термин Script API отдельно от `Widget`-иерархии; в реальных layout-файлах корневым элементом обычно выступает конкретный тип виджета (`class MyRootLayout` наследуемый неявно от `Widget`/`FrameWidget` через движковый механизм). **[Не подтверждено / требует проверки]**
- **`ImageWidget`** — виджет отображения растровой текстуры (`.paa`), поддерживает установку цвета через `SetColor`, установку изображения через `LoadImageFile`/задание в layout-атрибуте.
- **`TextWidget`** — виджет отображения текста, поддерживает шрифт, размер, цвет, выравнивание.
- **`ButtonWidget`** — интерактивный виджет-кнопка, обрабатывающий события нажатия через `OnClick`/скриптовые обработчики в связанном классе `UIScriptedMenu`/`ScriptedWidgetEventHandler`.

Привязка layout к скрипту выполняется двумя основными способами: **[Подтверждено: DayZ Script API]**

```csharp
// Loading a .layout file from script (typical inside a ScriptedWidgetEventHandler / UIScriptedMenu)
class MyMenu extends UIScriptedMenu
{
    override Widget Init()
    {
        layoutRoot = GetGame().GetWorkspace().CreateWidgets("MyMod/gui/layouts/my_menu.layout");
        return layoutRoot;
    }
}
```

```csharp
// Alternative: creating/finding a widget instance directly from a parent widget
Widget root = GetGame().GetWorkspace().CreateWidgets("MyMod/gui/layouts/my_menu.layout", parentWidget);
Widget imageWidget = root.FindAnyWidget("MyImageWidgetName");
```

### 3.2 Особенность цвета: ARGB, а не RGBA

**[На основе vanilla-скриптов]** (наблюдаемое поведение в существующих layout-файлах и вызовах `SetColor`) — явного отдельного параграфа в официальной документации, фиксирующего именно это как "особенность", в рамках доступных источников не обнаружено, но порядок байт ARGB широко подтверждается практикой использования `ARGB()`/`ARGBF()` хелперов в скриптах DayZ.

Цвет в Enfusion-виджетах (в том числе через `.layout` и через `SetColor` в скрипте) задаётся в порядке **ARGB** (Alpha-Red-Green-Blue), а не привычного веб-разработчикам RGBA:

```csharp
// ARGB order: Alpha, Red, Green, Blue — NOT RGBA
widget.SetColor(ARGB(255, 255, 0, 0)); // fully opaque red
widget.SetColor(ARGB(128, 0, 255, 0)); // 50% transparent green
```

Практическое следствие: при переносе цветовых значений из веб/дизайн-инструментов (которые обычно оперируют RGBA или HEX `#RRGGBBAA`) альфа-канал необходимо переставлять на первое место вручную — иначе цвет и/или прозрачность будут заданы неверно (типичная ошибка — "непрозрачный" элемент внезапно становится полупрозрачным или наоборот, потому что первый байт по ошибке трактуется как красный канал вместо альфы).

### 3.3 Overlay-layout поверх основного интерфейса

**[Не подтверждено / требует проверки]** — общий принцип наложения дочерних виджетов через `CreateWidgets(..., parentWidget)` подтверждён механизмом Script API (см. §3.1), но конкретно тема "overlay-layout корректно наследует текстуры/цвета основного интерфейса" как задокументированное поведение не найдена в доступных источниках. На практике (по наблюдаемым паттернам в модах сообщества) overlay-окна создаются как отдельный `.layout`, инстанциируемый с указанием родительского `Widget` через `CreateWidgets(path, parentWidget)`, что делает его частью того же дерева виджетов и, соответственно, того же UI-контекста (шрифты по умолчанию, viewport, масштабирование под текущее разрешение), но собственные цвета/текстуры каждого виджета всё равно задаются явно в его собственном layout/скрипте — автоматического "наследования" конкретных цветов от родителя как языковой механики не подтверждено. Требуется проверка по официальному Script API или у практикующего UI-разработчика мода.

## 4. Конвертация PNG → PAA

### 4.1 Инструменты конвертации

**[На основе общепринятой практики сообщества]** — `.paa` — проприетарный формат текстур Bohemia Interactive (Packed Array format), используемый во всех играх на движках Real Virtuality/Enfusion.

- **TexView2** — GUI-инструмент из состава Mikero Tools для просмотра и конвертации текстур в/из `.paa`.
- **ImageToPAA** — консольная утилита из состава Mikero Tools для пакетной конвертации PNG (и других форматов) в `.paa`.
- **Workbench (DayZ Tools)** — официальный инструмент Bohemia Interactive также содержит встроенные средства импорта текстур с автоматической конвертацией в `.paa` при импорте в проект аддона. **[требует проверки]** точного названия соответствующего инструмента/пайплайна внутри текущей версии Workbench.

### 4.2 Требования к исходному PNG

**[На основе общепринятой практики сообщества]**

- Размер текстуры должен быть степенью двойки (`power of two`) по каждой стороне: 32, 64, 128, 256, 512, 1024, 2048 и т.д. — несоблюдение может привести к некорректной работе мип-мэппинга или отказу инструмента конвертировать файл.
- Формат сжатия задаётся при конвертации:
  - **DXT1** — для текстур без альфа-канала (или с 1-битной прозрачностью), меньший размер файла.
  - **DXT5** — для текстур с полноценным альфа-каналом (плавная прозрачность), больший размер файла по сравнению с DXT1.
  - Выбор формата зависит от того, требуется ли текстуре прозрачность/полупрозрачность (например, для `ImageWidget` с полупрозрачными элементами UI типична DXT5).
- Мип-уровни (mipmaps) обычно генерируются автоматически инструментом конвертации (TexView2/ImageToPAA/Workbench) на основе базового изображения — ручная подготовка отдельных уровней не требуется в стандартном пайплайне. **[требует проверки]** — детали генерации (алгоритм фильтрации и т.п.) не задокументированы в доступных источниках.
- Расположение итогового `.paa` относительно структуры PBO: файл размещается в директории данных мода (по конвенции DayZ-модов — часто в поддиректории `data/` или `gui/textures/` внутри структуры мода, например `MyMod\gui\textures\my_icon.paa`), которая упаковывается в тот же PBO, что и остальные ресурсы мода. Путь, указанный в `.layout`/`config.cpp`, — это путь внутри виртуальной файловой структуры PBO (с префиксом имени PBO/пака), а не физический путь на диске разработчика.

### 4.3 Подключение `.paa` в `.layout` через `ImageWidget`

**[На основе vanilla-скриптов]** — связывает разделы §3 и §4: результат конвертации из §4.1–4.2 используется как источник изображения для `ImageWidget`, описанного в §3.1.

```csharp
// Setting a converted .paa texture on an ImageWidget from script
ImageWidget icon = ImageWidget.Cast(root.FindAnyWidget("MyIconWidget"));
icon.LoadImageFile(0, "MyMod\\gui\\textures\\my_icon.paa");
```

В текстовом `.layout` путь к текстуре указывается как строковый атрибут соответствующего `ImageWidget`-узла, ссылающийся на тот же PBO-относительный путь, что и при вызове `LoadImageFile` из скрипта (см. §4.2 про расположение файла относительно структуры PBO). Оба способа (статически в `.layout` и динамически из скрипта через `LoadImageFile`) сосуществуют: путь в `.layout` задаёт текстуру по умолчанию при создании виджета, а `LoadImageFile` позволяет заменить её в рантайме (например, для динамических иконок предметов).
